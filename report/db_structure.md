## 1. 바꾸기 전과 후

바꾸기 전에는 모든 자료가 `documents` 한 표에 섞여 있었다. 어떤 문서가 몇 개 들어 있는지 한눈에 보이지 않았고, 이전 버전인 PRD v0.2까지 같이 검색되어 답이 엇갈릴 수 있었다. 자료를 추가하려면 챗봇 코드를 고쳐 다시 배포해야 했다.

바꾼 뒤에는 표를 **역할별로** 나누고, 각 문서에 **섹터**를 붙였다.

```
doc_sources (문서 목록, 10줄)             doc_chunks (검색용 조각, 약 170줄)
┌─────────────────────────────┐          ┌──────────────────────────────────┐
│ id · slug · title           │ 1 ─── N  │ id · source_id → doc_sources.id │
│ sector (기획 / 현장·데이터 / │◀─────────│ chunk_index (문서 안 순서)        │
│   AI 모델 / 하드웨어 / 홈페이지)│          │ section · content · embedding    │
│ path · version · is_latest  │          └──────────────────────────────────┘
└─────────────────────────────┘
                                          chat_logs (대화 기록)
섹터별 보기: chunks_planning · chunks_field  question · answer · sources
            chunks_ai · chunks_hardware     sector · chunk_ids · latency_ms
            chunks_homepage · source_overview
```

---

## 2. 표 설명

**doc_sources (문서 목록)**: 챗봇이 읽는 자료 10개를 한 줄씩 적은 표다. 문서 이름, 섹터, 깃허브 경로, 버전, 최신 여부가 들어 있다. 새 보고서를 추가할 때는 코드를 고칠 필요 없이 이 표에 한 줄을 넣고 자료 저장을 실행하면 된다. `is_latest`가 false인 문서(PRD v0.2)는 기본 검색에서 빠진다.

**doc_chunks (검색용 조각)**: 문서를 제목 단위로 잘게 나눈 조각과 임베딩(의미를 담은 768개 숫자)을 저장한다. 각 조각은 `source_id`로 어느 문서에 속하는지 연결되고, `chunk_index`로 문서 안의 순서를 알 수 있다. 문서가 지워지면 그 조각도 함께 지워진다.

**chat_logs (대화 기록)**: 질문과 답변에 더해, 챗봇이 어느 섹터에서 찾았는지(`sector`), 어떤 조각을 참고했는지(`chunk_ids`), 답하는 데 몇 ms 걸렸는지(`latency_ms`)를 기록한다. 답변이 이상할 때 어떤 자료를 보고 답했는지 거꾸로 추적할 수 있다.

**섹터별 보기(view)**: `chunks_planning`(기획), `chunks_field`(현장·데이터), `chunks_ai`(AI 모델), `chunks_hardware`(하드웨어), `chunks_homepage`(홈페이지)는 해당 섹터의 조각만 문서 이름, 순서와 함께 보여준다. 읽기 어려운 임베딩 숫자 대신 임베딩 완료 여부만 표시한다. `source_overview`는 섹터별·문서별 조각 수와 임베딩 완료 수를 한눈에 보여준다.

## 4. RAG가 좋아진 점

**섹터 먼저 고르기**: 질문에 들어 있는 단어로 섹터를 먼저 고른다. 예를 들어 "MCU는 몇 개 써?"는 하드웨어, "왜 YOLO26n을 골랐어?"는 AI 모델, "투자 회수 기간은?"은 기획 섹터에서만 찾는다. 검색 범위가 좁아져 관계없는 문서의 비슷한 문장이 끼어들지 않는다. 섹터를 정할 단서가 없거나 두 섹터가 같이 나오면 전체에서 찾고, 고른 섹터에서 찾은 조각이 3개 미만이어도 전체로 다시 찾는다.

**이전 버전 제외**: PRD v0.2처럼 최신이 아닌 문서는 기본 검색에서 빠져서, 예전 결정(예: MobileNetV3)과 최신 결정(YOLO26n)이 섞인 답을 줄인다.

**출처가 깔끔해짐**: 답변 아래 참고 자료가 "하드웨어 설계서 · 3.4 MCU 개수와 배치"처럼 문서 이름과 절 제목으로 표시된다.

**바뀐 부분만 갱신**: 자료 저장을 다시 실행하면 문서마다 바뀐 조각만 지우고 추가하며, 순서만 바뀐 조각은 번호만 고친다. 그대로인 조각은 임베딩을 다시 만들지 않아 Gemini 무료 사용량을 아낀다.

---

## 5. 표를 섹터마다 완전히 따로 만들지 않은 이유

섹터마다 표를 따로 만들면(`hardware_chunks` 표, `ai_chunks` 표 등) 질문이 어느 섹터인지 애매할 때 표 여러 개를 각각 검색해 결과를 합쳐야 해서 느려지고, 표마다 같은 검색 함수와 색인을 따로 관리해야 한다. 그래서 실제 데이터는 역할별 표 하나에 두고 섹터를 칸으로 구분했으며, 사람이 읽기 좋도록 섹터별 **보기(view)**를 따로 만들었다. 저장은 한곳, 보기는 섹터별로 나누는 방식이다.

## 6. 옮긴 방법

기존 `documents` 표의 조각 170개와 임베딩을 SQL로 `doc_chunks`에 그대로 옮겼다. 그래서 임베딩을 다시 만들 필요가 없었다(Gemini 사용량 0). 옮긴 뒤 챗봇이 정상적으로 답하는 것을 확인하고 기존 `documents` 표와 `match_documents` 함수를 정리했다.
